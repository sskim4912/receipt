# EAS 로그인 이후 대기 최적화 — 2026-10-30

`eas_card_automation.py`는 정상 원본 그대로 유지한다. Edge 실행, 사람이 하는 SSO 로그인,
로그인 완료 감지와 로그인 뒤 2초 대기, 브라우저 유지 함수는 변경하지 않는다.
공개 저장소나 업데이트 묶음에 회사 원본을 포함하지 않는다.

`eas_receipt_bridge.py`의 실제 실행 경로에서 `ResponsiveBaseline`이 로그인 이후 두 단계를 담당한다.

- 목록 이동 뒤 무조건 4초를 쉬는 대신, 기존 목록 그리드가 한 개 표시되는지 0.2초마다 확인한다.
  최대 20초를 기다리고 EAS 출처 및 정확한 목록 경로를 확인한다.
- 그리드 준비 후 공지가 없는 경우의 8초 반복 대기를, 기존 다음 공지 확인 간격인 2초의
  연속 무공지 구간으로 바꾼다. 공지가 나타나면 원본의 공지 발견·닫기 함수를 사용하고,
  공지 소멸을 확인한 뒤 무공지 구간을 처음부터 센다. 최대 공지 개수 제한을 유지한다.
- 늦게 나타난 공지나 알 수 없는 팝업은 거래 재대조 및 매 입력 전후 검사에서 중단한다.
  공지 출현 시점은 실제 회사 화면에서 반드시 확인한다. 지연 공지로 중단되면 임의로
  검사를 생략하지 말고 해당 단계의 대기를 조정한다.
- 상세 URL 확인의 폴링 간격은 0.5초에서 0.2초로 줄이되 최대 대기시간은 20초를 유지한다.
- 콘솔에는 정해진 단계 이름과 초 단위 소요 시간만 추가한다. 별도 로그 파일을 만들지 않는다.
  로그인 감지 시간은 사용자 로그인 시간도 포함한다. 두 사용자 확인창의 응답 시간은
  목록·상세·입력 단계 시간에서 제외한다. URL, 쿠키, 인증정보, 영수증 내용은 기록하지 않는다.

후보 유일성, 업체등록 Y, 확인 이후 목록 재대조, 승인번호·날짜·금액·카드 대조,
입력 승인, 세 항목만 Selenium 입력, Tab 이후 값 유지 확인을 모두 유지한다.
EAS 저장, 비용구분·계정과목, 웹 데이터 및 전표 O/X는 변경하지 않는다.

## 검증과 범위

업로드된 정상 원본 SHA-256은 인계 문서와 일치했다.
회사 원본은 체크아웃 밖에 보관하고 변경하지 않았다.

Python 검사:

```sh
.local/eas-env/bin/python -m unittest discover -s tools/eas -p 'test_eas_*.py' -v
```

59개 중 58개 통과, 1개 건너뜀. 건너뛴 검사는 체크아웃 안의 비공개 원본 해시 검사이며,
업로드 원본 해시는 별도로 확인했다. 신규 검사는 로그인 함수 위임, 목록 준비 감지,
외부 주소 중단, 무공지 구간, 늦게 나타난 공지, 닫기 실패, 알 수 없는 팝업,
개수 제한과 실제 진입 경로의 3개 항목 입력을 포함한다.

업로드 원본 함수를 사용하는 가상 시계·모의 DOM 비교에서, 그리드가 즉시 준비되고
공지가 없는 경우 목록 이동 후 대기는 기존 12.0초, 개선 코드 2.2초였다.
네트워크·React 로딩·거래 스캔·로그인·사람의 확인 시간은 이 수치에 포함되지 않는다.
실제 PC 전체 구간의 3배 단축을 확인한 결과가 아니다.

## 기존 PC 적용과 실측

현재 PC 설치본과 웹 배포에는 아직 적용하지 않았다. 전체 재설치나 URL 등록 변경은 필요 없다.
연결로 열린 Edge를 닫고, 등록된 설치 폴더의 `eas_receipt_bridge.py`만 백업 후 교체한다.
`eas_card_automation.py`, `eas_assistant.py`, `eas_protocol.py`는 덮어쓰지 않는다.

같은 조건에서 로그인 완료부터 입력 완료까지 시간을 측정한다. 로그인, 두 확인창의
사람 응답 시간과 자동 처리 시간을 나누어 비교하고, 콘솔의 `[소요 시간]` 줄로
다음 병목을 확인한다. URL 또는 전체 콘솔 화면 대신 단계 이름·초만 공유한다.
실제 로그인·공지·거래 대조·3개 입력·사용자 직접 저장은 PC에서 재확인해야 한다.
문제가 있으면 브라우저를 닫고 백업한 연결 파일로 복구한다.
